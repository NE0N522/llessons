# Проверки проекта

## Запуск

Требуется Node.js 20 или новее. Установи зависимости командой `npm ci`, затем запускай проверки из корня проекта:

```powershell
npm test
node --test test/stage5.integration.test.js
node --test test/rate-limits.test.js
```

Все тесты используют PGlite и локальный Chromium из Playwright; для запуска тестов интернет не нужен. Полный набор выполняется последовательно (`--test-concurrency=1`), чтобы браузерные сценарии не конкурировали за ресурсы.

## Финальный аудит (этап 7)

```powershell
npm run check:deploy
npm run check:secrets
npm run qa:browser
npm test
npm audit
```

`check:deploy` проверяет существование файлов, npm-команд и локальных ссылок в README/DEPLOY. `qa:browser` открывает публичные страницы, кабинеты, все активные уроки и образцы проектов в Chromium при 1280 и 375 px в светлой и тёмной темах; сохраняет снимки и JSON-отчёт в `report/stage-7/`. `npm test` — полный последовательный набор API, браузерных и интеграционных сценариев.

`check:secrets` ищет известные форматы ключей/токенов и PostgreSQL URL с паролем, выводя только путь и строку. Файл локального `.env`, базы и резервных копий намеренно исключены; они не должны входить в архив или Git.

## Flexbox-пилот редизайна

К приёмке добавлены проверка миграции заметок и шагов 23 → 29, тест роли преподавателя для закрытых материалов, а также браузерные сценарии Ctrl+K, пошаговой навигации, мобильных вкладок кода/результата и офлайн-урока. Итоговые значения и замечания записываются в [`ОТЧЁТ-приёмки.md`](ОТЧЁТ-приёмки.md).

`test/stage7.acceptance.test.js` проверяет публичность страницы данных и контакта, ссылку футера на всех HTML-страницах, а также вкладки задания: две на телефоне, три на планшете и две соседние панели на широком экране. Проверяется и управление вкладками клавиатурой.

Облачные действия в Render и Neon этим набором не проверяются. Для реального запуска отдельно проверь оба URL: `DATABASE_URL` с пулером для запросов приложения и `MIGRATIONS_DATABASE_URL` без пулера для миграций. Чек-лист для ручной проверки владельцем находится в `report/stage-7/ПРОВЕРКА.md`.

Резервное копирование проверяет все таблицы, объявленные в миграциях, восстанавливает связи классов между учебными годами и сбрасывает identity-последовательности. В облаке храни копии отдельно от файловой системы Render; проверка восстановления выполняется только на пустой тестовой базе.

## Этап 5

`test/stage5.integration.test.js` проверяет права учителя/ученика, пять форматов заданий, скрытие ключей и исходников образца, баллы теста, подсказки, правило «Без подсказок», автопроверки с computed style, версии, обязательный комментарий при возврате, комментарии к строкам, сроки и снятие штрафа, вопросы, объявления, приватность сходства и конфликт заметок.

Playwright проверяет редактирование в CodeMirror, live-правила, закрытие и повторное открытие задания и урока без сети, восстановление IndexedDB, конфликт локальной/серверной версии, повторы после 500 и 429, постановку отправки в очередь и её доставку после восстановления соединения. UI задания ученика и окна проверки учителя снимается при ширине 1280 и 375 px в светлой и тёмной темах; тест проверяет горизонтальное переполнение.

Скриншоты сохранены в `report/stage-5/`. Тест намеренно не считает сетевые ошибки во время отключённой сети дефектом. Холодный старт и состояние реальной облачной базы в этой среде не проверяются.

## Этап 6

`node --test test/stage6.integration.test.js` покрывает границы аналитики 40×40, пороги риска, группировку ошибок, проверку владения классом, экспорт Excel с формулой среднего и форматом дат, а также PDF-отчёт. PDF проходит извлечение кириллического текста и рендерится в PNG для визуальной проверки.

Интеграционный сценарий готовит класс из 30 учеников, измеряет аналитику и генерацию Excel/PDF, затем выполняет перенос, выпуск и явное обезличивание. Он проверяет сохранение оценок по учебному году, вход ученика из архива, запрет черновика/отправки/ответа на тест, подтверждение очистки данных и сохранность оценок.

Playwright снимает вкладку аналитики, мастер закрытия года и архивное задание ученика при 1280/375 px в светлой и тёмной теме. В каждом состоянии проверяется отсутствие горизонтального переполнения и ошибок консоли. Отчёт, снимки, книга Excel, PDF и его PNG находятся в `report/stage-6/`.

## Нагрузка 30 учеников

`test/rate-limits.test.js` создаёт 30 виртуальных учеников с одного IP, выполняет 12 сохранений на ученика с интервалом 5 секунд и затем проверяет индивидуальную границу 30 запросов в минуту. Для каждого сохранения измеряются задержки; печатаются число запросов, число ответов 429, общее время, p50 и p95.

Последний полный прогон `npm test` на локальной PGlite: 360 запросов, 0 ответов 429, 55,4 секунды, p50 243,6 мс, p95 292,7 мс. Ранний прогон показывал p50 977,7 мс и p95 1177,1 мс. Разброс зависит от нагрузки локальной среды; это функциональные замеры, а не оценка пропускной способности Neon/Render. На production нужно повторить с реальными конфигурацией, TLS, сетью и пулом соединений.

Для отдельного пяти­минутного измерения этапа 7 запусти `npm run loadtest`. По умолчанию скрипт создаёт 30 временных учеников, посылает по одному запросу каждые 5 секунд (12 в минуту на ученика), считает p50/p95, ошибки и ответы 429 и записывает результат в `report/stage-7/loadtest.json`. Можно сократить локальный пробный запуск флагами `--students`, `--duration-seconds` и `--interval-seconds`. Скрипт использует локальную PGlite и не меняет production-базу; замер не предсказывает производительность Render/Neon.
